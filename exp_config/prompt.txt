Build a production-grade short-stay rental marketplace platform where both guests and hosts have their own AI agent — one finds and manages stays, the other runs the property — so the platform operates itself and both sides only approve decisions. Short-stay rental marketplaces created two new jobs nobody wanted. For guests — searching, comparing, messaging hosts, managing check-ins, chasing refunds when things go wrong. Every trip is a project. For hosts — setting prices, updating calendars, responding to inquiries, coordinating turnovers, handling complaints. Every listing is a part-time job.

Both sides spend most of their time on operations that could be handled for them. The marketplace connects supply and demand, but nobody manages what happens before, during, and after the stay. What we are designing is not a demo or conceptual mockup, but a realistic platform-level system combining marketplace dynamics, persistent state, agent-driven decision loops, and multi-party interactions.

What we built is a rental marketplace with two AI agents — one serving the guest and one serving the host — that handle operations on both sides of every booking. The agents communicate with each other, operate continuously over time, and interact with a shared marketplace environment, while neither acts without their human’s approval.

The system contains several roles. The Guest books stays and enjoys trips, approving or rejecting what their agent proposes, and never has to chase, coordinate, or complain directly. The Guest Agent finds stays matching the guest’s preferences, manages bookings, handles check-in logistics, detects problems during the stay, and acts on the guest’s behalf when things go wrong. The Host owns the property and sets the standards, approving or rejecting what their agent proposes and never having to manually price, respond, or coordinate. The Host Agent manages listing availability and pricing, responds to inquiries, coordinates turnover between guests, handles guest communication during stays, and flags issues that need the host’s attention. The Admin acts as the platform operator, managing marketplace rules, mediating disputes the agents cannot resolve, and monitoring platform health.

Each agent operates the same continuous loop on behalf of its human. The Monitor stage means the agent continuously watches all active bookings, listings, and communications, with activity always visible. The Detect stage catches events that need action such as new inquiries, pricing opportunities, schedule conflicts, problems during a stay, or review windows. The Propose stage puts a ready-to-approve action in front of its human in plain language — not an alert but a solution. The Approve stage allows the human to approve or reject in one tap, and no action is ever taken without explicit consent. The Act stage executes the decision immediately, such as responding, adjusting prices, rebooking, filing complaints, or coordinating turnovers. The Confirm stage updates the state so the human sees the result, and if execution fails, the loop restarts with a revised proposal.

The two agents also communicate with each other. When the guest agent requests early check-in, the host agent evaluates turnover feasibility and proposes it to the host. Both humans remain in control while the agents handle the negotiation.

The platform should support several key capabilities. The marketplace should support search and match, booking lifecycle management, multi-stay support, and long-lived interactions across multiple trips and properties. The guest agent should support pre-trip planning, during-stay monitoring, and post-stay resolution and learning. The host agent should support listing management, pricing adaptation, guest communication, turnover coordination, and issue handling. Agent-to-agent communication should support negotiation, dispute escalation, and full transparency of interactions.

Finally, the system should follow several cross-cutting principles: plain language, an approval gate, transparency, and a mobile-first interaction model. The system should be designed as a realistic production-style platform that considers components, persistent state, data flow, agent behavior, and marketplace dynamics rather than a simplified prototype.
